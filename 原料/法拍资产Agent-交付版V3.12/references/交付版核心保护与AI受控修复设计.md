# 法拍资产Agent交付版核心保护与AI受控修复设计

## 1. 设计目标

交付版需要同时满足：

1. 普通用户和外部AI不能直接修改采集、状态机、高水位、批次绑定和Excel规则核心；
2. 用户仍可正常写入配置、登录状态、高水位、断点、结果、日志和复核数据；
3. 运行异常时，用户可以把脱敏诊断信息交给自己的AI分析；
4. AI只能提出或生成白名单内的结构化修复方案，不能运行任意命令、改写任意文件；
5. 修复前可预览，修复后可回滚，并完整记录操作者、批次、原值和新值；
6. 核心被篡改时，程序不得继续采集、复核回写或推进高水位。

## 2. 必须承认的安全边界

### 2.1 “只读属性”不是安全机制

Windows文件的只读属性只能减少误操作。用户拥有文件或管理员权限时，可以取消只读、取得所有权或替换文件。

### 2.2 普通ZIP不能保留可靠的安装权限

把当前项目目录直接压缩后发送，用户解压出的文件通常由该用户所有。原电脑上的NTFS ACL不会作为可靠保护边界随ZIP交付。

### 2.3 管理员最终可以控制自己的电脑

无法在用户拥有管理员权限的电脑上绝对阻止其替换本地文件。可实现的可靠目标是：

- 普通使用流程无法误改核心；
- 未经发布者签名的核心修改会被检测；
- 被修改的程序不能继续执行关键业务；
- 官方升级只能接受开发者签名的软件包。

## 3. 推荐交付架构

```text
安装目录（普通用户只读）
├─ launcher.exe                 签名启动器和完整性校验入口
├─ app/
│  ├─ core.bundle              打包后的Agent与V2核心
│  ├─ core-manifest.json       文件清单、版本、SHA-256
│  ├─ core-manifest.sig        开发者私钥签名
│  └─ publisher-public-key     只含公钥
├─ node-runtime/               固定运行时与依赖
├─ public/                     已签名网页资源
└─ manuals/                    用户手册和FAQ

用户数据目录（当前Windows用户可写）
%LOCALAPPDATA%\JudicialAuctionAgent\
├─ config/                     本机配置，不保存明文API Key
├─ agent-data/                 当前状态、任务历史、事件、日志
├─ state/                      scoped-tasks、高水位、断点、Edge Profile
├─ support/
│  ├─ bundles/                 脱敏诊断包
│  ├─ patches/pending/         待预览修复包
│  ├─ patches/applied/         已应用修复包和回滚记录
│  └─ backups/                 修复前原子备份
└─ cache/                      可安全清理缓存

用户自选结果目录
└─ YYYYMMDD（N）/
   ├─ 最终Excel
   ├─ batch-meta.json
   ├─ 采集进度与证据
   └─ 复核、摘要和异常报告
```

当前项目中的`bin/`、`src/`、`runtime/`、`public/`、核心`scripts/`、`references/`、`package.json`和锁文件均属于只读核心。`config/agent.local.json`、`agent-data/`、`path/`和结果目录属于可写数据。

## 4. 核心保护的四层机制

### 第1层：安装目录权限

- 使用安装器安装到`Program Files`，不要把裸源码文件夹作为正式交付品；
- 安装目录由Administrators/SYSTEM管理；
- 普通Users只有读取和执行权限；
- 可写状态全部迁移到`%LOCALAPPDATA%`或用户选择的结果目录；
- 安装器不得把真实配置、Cookie、Profile、API Key、历史结果打包进去。

该层主要防误操作，不作为唯一的防篡改依据。

### 第2层：数字签名和清单

发布时生成`core-manifest.json`，至少记录：

```json
{
  "schemaVersion": 1,
  "product": "法拍资产Agent",
  "releaseVersion": "",
  "buildId": "",
  "createdAt": "",
  "files": [
    { "path": "app/core.bundle", "sha256": "", "critical": true },
    { "path": "public/app.js", "sha256": "", "critical": true }
  ]
}
```

清单使用开发者离线保存的Ed25519私钥签名。交付包只包含公钥，绝不包含私钥、私钥备份或签名口令。

启动器先验证清单签名，再验证关键文件哈希。仅把文件哈希写在同一套可修改JavaScript中不够安全，因为攻击者可以同时修改校验器；校验入口应位于签名的启动器中。

### 第3层：关键操作前二次校验

以下操作前必须确认核心完整性状态为`verified`：

- 创建新采集任务；
- 恢复采集；
- 写入或推进高水位；
- 生成最终工作簿；
- 应用AI复核结果；
- 执行受控修复包；
- 安装升级包。

若校验失败，进入`integrity_blocked`：禁止上述写操作，但允许查看手册、查看历史、打开结果文件夹、导出诊断包和安装官方签名更新。

### 第4层：签名升级

- 只接受开发者私钥签名的完整版本或增量升级包；
- 升级前验证版本、签名、目标产品和最低兼容版本；
- 升级采用新目录写入、校验成功后原子切换；
- 保留上一个有效版本用于回滚；
- 用户AI生成的补丁绝不能进入核心升级通道。

## 5. AI受控修复中心

网页中的AI支持功能不应是“让AI自由编辑程序”，而应是以下闭环：

```text
发现异常
→ 生成脱敏诊断包
→ 复制标准AI诊断指令
→ 用户把诊断包和指令交给自己的AI
→ AI返回结构化修复建议或patch.json
→ Agent本地校验
→ 页面展示影响范围和回滚点
→ 用户确认
→ 白名单执行器原子应用
→ 自检
→ 成功归档 / 失败自动回滚
```

### 5.1 脱敏诊断包

诊断包建议使用JSON或ZIP，包含：

- 产品版本、buildId和核心完整性结果；
- 操作系统、Node和Edge版本；
- 当前`taskId`、`batchId`、`runName`、status、phase和statusMessage；
- allowedActions；
- 批次目录和文件存在性、大小、哈希，不默认包含完整业务记录；
- 分组完成摘要、缺失高水位键、计数和剩余数；
- Worker PID是否存活、锁身份、重试次数和最后错误；
- 验证状态，但不包含Cookie、验证码、短信码和表单内容；
- AI复核方式、候选数、进度和失败摘要；
- 最近日志的脱敏尾部；
- 配置字段名称和非敏感值。

必须排除或脱敏：

- API Key和密钥密文；
- Cookie、Authorization、浏览器存储和完整Edge Profile；
- 账号、密码、短信码和验证码；
- 无关的用户文件路径；
- 全量历史数据库；
- 用户未授权提供的完整房源数据。

生成后在本机再执行一次敏感模式扫描，例如`sk-`、`Bearer`、`Cookie:`、常见Token字段和手机号格式。

### 5.2 AI诊断指令

标准指令必须告诉AI：

- 只能分析附件中的诊断信息；
- 不得修改核心文件；
- 不得删除`path`、`scoped-tasks`、高水位、当前批次或历史结果；
- 不得清空断点、创建新任务或推进失败分组高水位；
- 不得输出任意PowerShell、CMD、Node代码作为自动执行补丁；
- 可先给出文字排查步骤；
- 如需机器修复，只能返回规定schema的JSON；
- 信息不足时必须声明，不得猜测taskId、batchId、工作簿或高水位。

### 5.3 允许的修复类型

建议第一版只开放低风险、可验证操作：

| 类型 | 允许动作 | 必要前置条件 |
|---|---|---|
| `restart_backend` | 提示并安全重启旧后台 | 无采集/复核Worker运行 |
| `release_stale_lock` | 释放失活Worker锁 | PID不存在且身份匹配失败 |
| `normalize_terminal_state` | 清理终态中的陈旧PID和验证标志 | 状态已是终态 |
| `reopen_verification` | 重新打开保留URL | taskId、batchId、owner一致 |
| `resume_collection` | 恢复同一采集批次 | 存在有效断点和身份绑定 |
| `resume_review` | 恢复同一复核批次 | 复核包和工作簿属于同一批次 |
| `rebuild_workbook` | 从同批次权威记录重建Excel | 记录非空、URL去重、批次一致 |
| `reexport_review_package` | 重新导出工作台复核包 | 最终工作簿和批次一致 |
| `retry_failed_review_items` | 仅重试技术失败候选 | 不修改已成功记录 |
| `repair_config_value` | 修改少量白名单配置 | 旧值哈希匹配且通过配置校验 |

第一版禁止自动执行：

- 任意文件路径写入；
- 任意shell、PowerShell、CMD、Node、Python命令；
- 修改`bin/`、`src/`、`runtime/`、`public/`或核心脚本；
- 删除或重置高水位；
- 推进失败、暂停或跳过分组的高水位；
- 删除历史结果；
- 修改最终Excel业务值；
- 从其他日期或“最新目录”猜测并合并批次；
- 自动绕过验证码；
- 安装npm包或下载并运行远程代码。

业务字段补采和人工数据更正应使用单独的证据型工具，不纳入通用故障补丁执行器。

## 6. 结构化修复包

建议schema：

```json
{
  "schemaVersion": 1,
  "patchId": "uuid",
  "createdAt": "ISO-8601",
  "generator": "user_ai",
  "diagnosticBundleId": "",
  "target": {
    "productBuildId": "",
    "taskId": "",
    "batchId": "",
    "runName": ""
  },
  "problem": {
    "code": "",
    "summary": "",
    "evidence": []
  },
  "operations": [
    {
      "type": "release_stale_lock",
      "preconditions": {
        "stateHash": "",
        "workerPid": null,
        "workerAlive": false
      },
      "parameters": {}
    }
  ],
  "expectedResult": "",
  "risk": "low",
  "requiresUserConfirmation": true
}
```

外部AI无权签署官方核心更新。`generator=user_ai`修复包只能进入受控执行器，并不等同于开发者签名包。

## 7. 修复执行器规则

1. 解析JSON，拒绝额外可执行内容和未知字段；
2. 验证schema版本、patchId和诊断包关联；
3. 验证当前buildId、taskId、batchId、runName；
4. 验证状态哈希和文件哈希，防止诊断后状态已变化；
5. 验证operation属于白名单；
6. 计算将读取、修改、创建的精确路径；
7. 页面显示预览、风险、原因、旧值、新值和回滚位置；
8. 用户明确确认；
9. 获取补丁互斥锁，禁止与采集、复核、缓存清理并发；
10. 创建原子备份；
11. 执行单个确定性操作；
12. 运行对应离线自检；
13. 成功后归档审计记录；
14. 任一步失败立即回滚，并禁止高水位推进。

不得采用`eval`、动态`import`用户文件、`child_process`执行补丁字符串或拼接shell命令。

## 8. 审计和回滚

每次应用修复记录：

- patchId和diagnosticBundleId；
- 用户确认时间；
- taskId、batchId和buildId；
- 操作类型；
- 精确文件；
- 修改前后哈希；
- 自检结果；
- 回滚状态；
- 不含密钥的错误摘要。

备份只保存被修改的小型状态文件，不复制完整Edge Profile。回滚必须校验当前文件仍等于补丁后的哈希，避免覆盖补丁后产生的新数据。

## 9. 网页“AI故障处理中心”的功能需求

该栏目建议包含：

1. 当前核心状态：已验证、已修改、版本过旧或无法校验；
2. “运行安全诊断”：只读检查状态、锁、批次、工作簿和高水位完整性；
3. “导出脱敏诊断包”；
4. “复制AI诊断指令”；
5. 问题类型选择：启动、采集、高水位、验证、Excel、AI复核、缓存、其他；
6. “导入AI修复方案”；
7. 修复方案预览：目标批次、前置条件、将修改内容、风险和回滚点；
8. “确认应用安全修复”；
9. “查看修复记录”；
10. “回滚最近修复”，仅在满足哈希前置条件时可用。

核心完整性失败时，页面必须明确显示“程序核心已被修改，采集和高水位写入已锁定”，不能仅显示普通运行错误。

## 10. 发布与安装流程

推荐流程：

1. 在干净构建环境执行全部离线测试；
2. 清除`agent-data`、真实配置、日志、Profile、Cookie、结果和密钥；
3. 构建`core.bundle`和固定运行时；
4. 生成manifest和SHA-256；
5. 使用离线私钥签名manifest和安装包；
6. 生成SBOM和版本说明；
7. 在全新Windows标准用户账户安装；
8. 验证普通用户不能写安装目录但能写用户数据目录；
9. 篡改任一关键文件，验证关键操作被阻止且仍可导出诊断；
10. 验证官方签名升级和回滚；
11. 再交付安装器，不交付裸源码ZIP。

如果业务上必须发送一个压缩包，应发送“便携启动器 + 签名核心包”，而不是可直接编辑的源码树；启动器每次启动和关键写操作前仍要验证签名。

## 11. 分阶段实施建议

### 阶段A：安全边界和诊断（低风险）

- 核心/数据目录分类；
- 脱敏诊断包；
- AI诊断提示词；
- 只读安全自检；
- 网页展示核心状态；
- 不开放任何自动修复。

### 阶段B：受控修复（中风险）

- patch schema；
- 白名单执行器；
- 预览、确认、备份、回滚和审计；
- 先开放重启、失活锁、验证恢复和同批次重建工作簿。

### 阶段C：正式防篡改交付（较大改造）

- 固定数据目录；
- 核心打包；
- 签名启动器；
- manifest签名；
- 安装器ACL；
- 签名升级和版本回滚。

## 12. 验收标准

- 普通用户不能通过正常UI改写核心；
- 修改关键核心后启动器能检测并阻止采集、高水位和复核回写；
- 私钥不出现在源码、安装包、日志或CI产物中；
- 用户配置、状态、高水位、Profile和结果仍可正常写入；
- 诊断包不包含API Key、Cookie和账号凭据；
- AI返回任意代码、未知操作或越界路径时被拒绝；
- 修复包必须绑定buildId、taskId和batchId；
- 修复前有预览和备份，失败自动回滚；
- 修复不会创建新任务、清空断点或隐式推进高水位；
- 核心完整性失败时仍能查看手册、历史和导出诊断；
- 正式交付不包含生产数据和真实浏览器Profile。
