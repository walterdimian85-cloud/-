# browser-skill 法拍信息采集工作指令

## 适用阶段与边界

本文件适用于任何使用browser-skill领取“阶段1：采集或断点续采集”任务的执行者。该阶段只负责从网页读取法拍信息并保存为可复核的结构化记录；不负责AI字段复核、去重、生成HTML/Excel、同步飞书或修改Agent程序。

开始前必须依次阅读：`E:\dsh\中间\通用智能体工作指令.md`、`E:\dsh\中间\采集复核与交接硬性规则.md`。本专用工具指令与硬性规则冲突时，以硬性规则为准。

若用户未明确任务，先询问：

> 请告诉我本次 browser-skill 采集的日期、地区、平台、状态（即将开始/已结束）、起止链接或高水位，以及是否为新采集或断点续采集。

收到任务后先声明：任务日期、地区/平台、输入链接、读取路径、输出路径、是否允许新建当天日期目录。本次默认不会启动法拍资产 Agent、不会改配置、不会生成产物、不会同步飞书。

本指令已经吸收 `E:\dsh\.workbuddy\memory\2026-08-28.md` 与 `采集经验对接-codex.md` 中可复用的规则。日志中的当日数量、脚本名和旧高水位不是长期配置，不得直接复用；本次高水位必须重新从用户、Agent 配置或当天进度文件确认。

## 固定路径与文件

- browser-skill 仅用于网页读取，采集结果统一写入：`E:\dsh\中间\法拍agent房源结果目录\YYYYMMDD`
- 当天目录不存在时，只有用户已明确“开始采集 YYYYMMDD”才可创建这一个日期目录；不得创建额外的临时、测试、最终版或重复日期目录。
- 不得覆盖或删除 Agent 已有的 `采集进度.json`、原始 JSON、复核文件、Excel 或 `batch-meta.json`。
- 本工具自己的文件固定为：
  - `YYYYMMDD_browser-skill补采记录.json`：本次已成功读取的记录数组；每完成一条立即追加保存。
  - `YYYYMMDD_browser-skill采集进度.json`：已完成链接、当前链接、失败原因、最近更新时间和待处理链接；用于断点继续。
  - `YYYYMMDD_browser-skill缺失清单.json`：记录“公告完整加载后仍缺失”或“公告等待满10秒仍未加载”的字段、原因和链接。

日期由用户指定，格式 `YYYYMMDD`。同日存在 `YYYYMMDD（1）` 等目录时，先查看 `目录说明.md`、批次状态和时间戳；无法判定主批次时暂停询问用户。

## 默认采集范围

除非用户另行指定，采集范围与法拍资产 Agent 相同：

- 省份：福建省。
- 城市：福州市、泉州市。
- 平台：阿里资产（PC端）、京东拍卖（PC端）。
- 站点分类：住宅用房、商业用房、工业用房。
- 状态：即将开始、已结束；不采集“正在进行”。
- 阿里资产默认不含破产清算。

高水位、起止链接和排序方向必须以用户本次指定内容或 Agent 当前任务配置为准；缺少时先问，不得凭历史链接猜测。

高水位的固定口径：高水位是上一次采集范围的边界，边界标的已属于上一批次。本次从列表顶部开始收集新记录，遇到高水位即停止，**不采高水位本身及其后的旧记录**。若调整过结束时间排序，必须重新抓列表并重建待采清单。

阿里列表参数：上新使用 `sort=504`，结束使用 `sort=600`，`hPurpose` 必须同时包含住宅、商业、工业；优先使用 `zc-paimai.taobao.com/wow/pm/default/pc/4b80fa` 列表。列表状态仅用于建队列，成交、流拍、撤回等最终状态以详情页为准。

## browser-skill 使用规则

1. 每次任务先运行 `bsk status`，确认扩展已连接；异常时运行 `bsk doctor`，不能继续时报告用户。
2. 必须按生命周期操作：`bsk session start` → 所有操作均带 `--session <会话ID>` → 完成、失败或暂停时均执行 `bsk session stop <会话ID>`。
3. 先用 `bsk snapshot` 读取页面；页面切换、刷新或导航后，元素引用失效，必须重新 snapshot。
4. `snapshot` 不完整时优先用页面求值读取 `document.body.innerText`；价格、面积、调查表字段不得只凭空快照判缺失。只有正文读取仍不足时才使用 HTML 或截图。
5. 不读取或导出 Cookie、令牌、密码、登录信息；不报名、出价、收藏、提醒或提交任何交易操作。
6. 出现登录、验证码、短信验证或风控时，立即调用 `bsk request-help` 交给用户；用户交还控制权后重新 snapshot，再继续。
7. 不连续盲点两次以上；同一操作两次无进展时，记录原因并暂停询问用户。

长任务一次只允许一个脚本控制同一 session。每20—30分钟检查 session；出现 `session not registered` 或中断时重建会话，并依靠进度文件续采。禁止清空进度重跑。后台任务直接写日志，不用会造成输出缓冲的尾部管道。

## 建队列、过滤与断点规则

1. 先一次性抓取用户指定的全部列表范围，保存“规范 URL＋列表标题＋城市＋状态＋顺序”，再生成固定待采清单；禁止边开详情边决定采什么。
2. 规范化URL时删除跟踪参数；阿里保留`sf_item/<标的ID>`，京东保留`paimai.jd.com/<标的ID>`。平台＋标的ID只是标识，不是跨阶段、跨轮次的唯一去重键。
3. 队列生成阶段只排除单独拍卖的纯车位、纯车库；独立储藏间保留，住宅/商业/工业与附属物一并处置时整体保留。
4. 不得因为链接存在于累计HTML就从采集队列跨阶段删除。上新与结果分阶段处理，最终复合去重在阶段3完成。
5. 先读取 `YYYYMMDD_browser-skill采集进度.json`，从待采清单排除已完成链接。公告未完整加载时累计等待上限为10秒；满10秒仍为空或不完整则写缺失清单并继续。
6. 每条采完必须校验当前 URL、页面标题与清单标题一致；不一致视为上一页残留或串数据，重新打开核验，不得保存。
7. 进度文件必须实时写入总数、完成数、剩余数、当前链接和更新时间。长批次按每10条或每10分钟主动报一次进度，报告后继续运行；除验证码、登录、风控或缺少关键参数外，不等待用户发送“继续”。
8. 只有固定待采清单全部处理并写盘后才能报告完成。进程或 session 意外停止时立即重建并从断点恢复；没有活动会话或进程时不得声称仍在采集。

## 每条标的的强制采集顺序

1. 从列表获取详情链接，去除跟踪参数，保存规范详情页链接作为记录标识；最终去重还必须结合轮次、阶段和拍卖时间。
2. 打开详情页，先采集详情页、标的物介绍和调查表已明确展示的字段，并保存字段来源与原文证据。
3. 先判断必采字段是否已完整且有可靠证据：**已完整则立即保存并进入下一条，不打开也不等待竞买公告。**
4. 仅当仍有必采字段缺失时，才点击或打开“竞买公告/公告”，并**滚动到公告区使其进入可视区域**；重新 snapshot 后才判断公告内容是否已经完整出现。
5. 公告区进入可视区域后仍在加载、出现骨架屏、空白区、加载提示或内容继续渲染时，才开始等待并重新读取；累计等待上限为10秒。不得只凭页面 DOM 中的公告占位文字判定超时。
6. 公告在10秒内加载完成后，只补读仍缺失的字段。公告等待满10秒仍未加载或仍无法补齐时，在缺失清单记录`公告10秒未加载`、受影响字段、页面状态、已检查位置和链接；受影响字段保留为`待补采`，然后**立即进入下一条**。公告已完整加载且已重新读取后字段仍无可靠证据时，才写为`未找到`。
7. 每条成功或待补采记录都立即更新补采记录和进度文件；不得等整批结束才保存。

禁止在公告仍加载时依据空白或不完整页面把字段写成`未找到`；本项目统一等待上限为10秒，满10秒按第6条登记为`待补采`后立即进入下一条。

## 必采字段与统一口径

每条记录必须包含下列字段；没有可靠证据时保留 `未找到`，不得推测或用不相关数据代替：

1. `所在省份`：固定为福建省。
2. `城市`：福州市或泉州市；优先页面所在地/正式标题，其次法院交叉确认。
3. `区域`：区、县或县级市；冲突或缺失需记录待复核。
4. `标的名称`：保留可识别的具体坐落、小区/园区、楼栋、单元、房号、商铺或车位等定位信息；不虚构地址。
5. `小区名称（仅供参考）`：按采集复核与交接硬性规则§7依次从页面、标题/公告正式项目名和历史名称池精确匹配；不得使用标题或地址的截断片段、街道、镇、村等行政区片段。无可靠完整名称时写`未找到`，不猜测。
6. `标的类型`：车位、住宅、别墅、商业、工业之一。住宅用房中的车位为车位，含别墅为别墅，其余为住宅；商业用房为商业；工业用房为工业。
7. `平台`：阿里资产或京东拍卖。
8. `发拍次数`：一拍、二拍、再次拍卖、变卖；无法确认写`待核验`。
9. `拍卖时间`：即将开始取明确开拍时间；已结束取最终竞拍结束时间；不得推算。
10. `是否成交`：即将开始写`未开始`；已结束写是、否或待核验。已撤回、已中止、已暂缓的标的写入删除/异常清单，不进入补采记录的有效数据和后续交接。
11. `处置法院`：页面处置机构或公告中的人民法院全称。
12. `面积/㎡`：数值或`未找到`；同时写明面积原文和来源。
13. `起拍价格`：人民币元数值或`未找到`。仅在可靠识别为变卖且起拍价缺失时才可使用变卖价。
14. `评估价`：人民币元数值或`未找到`；页面“市场价”按本项目口径作为评估价，保证金和起拍价不得代替。
15. `成交金额`：已成交时取明确拍下价/成交价；未结束和未成交为0。
16. `竞买记录`：已结束时读取竞买/应买/竞价/出价记录；未结束留空，流拍为0。
17. `报名人数`：已结束时读取；未结束留空。
18. `备注`：记录主标的与附属物面积、状态说明和其他不能丢失的事实。
19. `网站链接`：规范详情页链接，作为记录标识；不得单独据此跨阶段删除。
20. `_fieldEvidence`：每个关键字段的值、原文、来源区块（详情/竞买公告/调查表等）、读取时间和置信度。

明确排除字段：`保证金`、`加价幅度`、`围观人数`。无论上新或结果都不主动提取、不写入补采记录、不进入 `_fieldEvidence`、不校验、不回传；观察结果中偶然出现时直接忽略，不为这些字段增加页面操作或打开公告。

最终 Excel 计算字段可同时提供，但不得伪造：`起拍单价-元/㎡`、`折扣率(%)`、`溢价率`、`成交单价`。无法计算时留空。

## 面积、价格、状态的不可突破规则

- 面积查找顺序：详情页正文/调查表 → 拍品介绍 → 竞买公告或变卖公告；只有前一层不足时才进入下一层。
- 同一证据的面积关键词优先级：建筑面积 → 房屋建筑面积 → 总建筑面积 → 产权建筑面积；多套合并拍卖有“总计”行时取总计，并在备注保存分项。
- 不得将土地、宗地、占地、分摊、公摊面积作为主面积。
- 住宅/商业与储藏间、附属间、柴火房、车位、车库并列时，如页面只给出合并建筑面积，`面积/㎡`直接采用该建筑面积；如分别列出且有总建筑面积，取总建筑面积；没有总计时取住宅/商业主面积。所有分项或合并原文写入`备注`，土地、占地、分摊、公摊面积仍不得作为主面积。
- 多个同类住宅或同类商铺明确合并拍卖且编号、面积逐项对应时可汇总主面积，并把分项写入`备注`；不得把未列入标题或附属物面积混入。
- 面积大于10000㎡，或起拍价÷面积大于100000元/㎡、小于500元/㎡时，备注必须含“数据疑似有误”及具体原因。
- 阿里成交以明确“本场已结束”及“拍下价”判断；阿里流拍以“本场已流拍”判断。冲突时优先流拍文案。仅列表显示结束但详情无结论时写`待核验`。
- 阿里评估价同时匹配“评估价”和“市场价”；变卖无起拍价时按“变卖价 → 变卖预缴款”取起拍价格；拍下价就是成交金额。
- 成交、流拍必须采报名人数。小区名称必须从标题、正文、公告或历史 HTML 的精确名称池补齐；均无证据时写`未找到`，不得猜测或以截断文本代替。
- 缺失识别必须覆盖 `null/None`、空字符串、`未找到`、`待补采`。整批完成后只定向补采缺失链接，禁止重新全量采集。

## 结束条件与回报

采集结束后停止 browser-skill 会话，并向用户报告：采集日期、平台/地区/状态、成功数、失败数、公告完整加载后仍缺失的字段数、断点文件路径、补采记录路径、缺失清单路径，以及是否需要进入阶段2或阶段3。

不得自行进入复核、去重、交接或产物生成阶段。
